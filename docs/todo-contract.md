# todo 任务契约改造方案（草稿 2026-12-19，待用户拍板后实施）

> 目标一句话：todo 从「可用的规划工具」升级为「任务契约」——每个会话每轮必出清单、
> 进度实时同步、轮次收尾状态干净、UI 按 DSH TodoDock 视觉重做。
> 本轮只出方案，不改生产代码。

---

## 0. 现状盘点（与缺口）

| 面 | 现状 | 缺口 |
|---|---|---|
| 工具 `internal/tools/todo.go` | 全量替换写入；active≤1 硬校验；空清单=清空合法 | 无 content 唯一性校验；回显只有「N 项，done M」计数，无进行中项/收敛态提示 |
| 会话状态 `internal/agent/turn.go` | `WithTodoSink` ctx 注入 → `s.todos` 内存字段 + `TodoUpdatedEvent` | **不落库**（store 无 todos 列，重启丢失）；模型对清单现状无感知（不更新了模型也不知道） |
| 子会话 `internal/agent/dispatch.go` | `childEmitter` **拦截** `TodoUpdatedEvent`（清单归子会话自己） | 子会话清单在前端只有子会话标签页能看到（双投已有），主时间线派发卡上无进度；主 Agent 上下文完全感知不到子会话进度 |
| 提示词 `internal/agent/prompt.go` | 三档 todoPromptRule（strict 默认/normal/off）注入守则第 5 条 | strict 是「动手前先建清单」，不是「每轮必出」；无轮收尾纪律条款 |
| 前端计划条 `frontend/src/aicss/TodoList.tsx` | 已是 DSH vendor 改造：三态图形（勾/箭头/虚线环）、滚动计数、折叠 | 头部只有 done/N，无「N done · M 进行 · K 待办」计数标签；无进行中进度环；唯一呈现面 = Composer 计划条 |
| 时间线 | `todo` 工具调用渲染成普通工具行（args JSON） | 无 TodoRow 摘要（N done · M 进行），视觉上「清单出来之后没痕迹」 |
| 派发 | `agent_dispatch` 只有 task/session 参数 | 主 Agent 无法把拆好的清单交给子 Agent；dispatch 卡无进度徽标 |

## 1. 数据模型与状态机

### 1.1 数据结构（不变）

`TodoItem { content, status: pending|active|done }`，全量替换语义。三态不改——
DSH TodoDock 的视觉（勾/渐变环/虚线环）恰好按三态渲染，加第四态（如 blocked）没有视觉与
语义收益。

### 1.2 持久化（B6）

- `sessions` 表加一列：`todos TEXT NOT NULL DEFAULT ''`（JSON 数组；空串 = 无清单），
  幂等 ALTER，与 `parent_id`/`context_usage` 等同一条迁移路径（`internal/store/store.go`）。
- **写路径**：`turn.go` 的 todo sink 里落库（现有 `s.todos = items` 处加 `st.UpdateTodos(id, items)`）。
  每次 todo 调用写一次，WAL 下开销可忽略；清单是个位数条目的小 JSON。
- **读路径**：会话恢复（`Latest`）时读回 `s.todos`，`Snapshot.Todos` 与 `chat.history`
  的 `todos` 键随之在重启后仍然正确。
- **子会话归档形态**：派发收尾（`runDispatch` 正常结论分支）把子会话行的 todos 写为
  **定格值**（finalTodos）——之后子会话不再动清单（除非被续跑）。父会话不存子清单，
  主时间线从 dispatch 块读。

### 1.3 不做事件级溯源（拍板过，理由记录）

清单是**状态**不是**历史**，UI 只消费当前快照。溯源记录已经天然存在：`todo` 的每次
tool call + result 本来就落在 messages 历史里（`session_search` 也能搜到），再写一份
todo_events 表是纯冗余，还要多一条压缩/统计的兼容面。DSH 的事件溯源写会话日志，在我们
这里对应物就是「工具调用历史」，已覆盖。

### 1.4 清单状态机（A4 残留策略的核心）

```
                    ┌────────────────────────────────────────────┐
                    │  主会话（跨轮长会话）                        │
                    │                                            │
  新一轮开始 ──────►│ 无清单 ──► strict 档提示词要求本轮出清单      │
                    │ 有清单(未完成) ──► 轮首快照注入（模型可感知）  │
                    │ 有清单(全done)  ──► 轮首收敛通告（可重建）    │
                    │                                            │
  轮收尾 ──────────►│ 校验：仍有 active/pending → 被动通告入队      │
                    │  （下一轮提示词可见，不硬阻塞）               │
                    │ 全 done → 保留不清空（成就态 + 历史上下文）    │
                    └────────────────────────────────────────────┘

                    ┌────────────────────────────────────────────┐
                    │  子会话（一次派发 = 一个生命周期）            │
                    │                                            │
  派发开始 ────────►│ 初始清单 = dispatch.todos（主 Agent 拆的，    │
                    │  可选）或空（子 Agent strict 档自拆）         │
                    │ 执行中 ──► todo.updated 带 dispatch_id 实时  │
                    │  双投：子会话页实时计划条 + 主时间线卡徽标     │
                    │                                            │
  派发结束 ────────►│ 清单定格归档（sessions.todos 定格值）         │
                    │ DispatchEnd 带 finalTodos → 卡上定格显示     │
                    │ 主 Agent 结果文本追加最终清单状态（N/M+残留项）│
                    └────────────────────────────────────────────┘
```

**主子差异的理由**：主会话是多轮长对话，跨轮保留清单才能呈现整体任务进度，轮结束清空
（DSH turn/start 语义）会把「改 5 个文件跑 3 轮」这种任务的第 1 轮成果抹掉；子会话是
一次派发的执行现场，派发结束即定格——它的生命周期与 dispatch 卡同构，卡就是它的归档。
**残留**由此有明确定义：主会话 = 跨轮仍 active/pending 且模型从未交代；子会话 = 定格时
仍有未完成项（如实定格显示，主 Agent 结果文本会点名）。

## 2. 生成与约束（模型侧，A 组）

### 2.1 「每轮必出 todo」的落地（A1）

三层，从软到硬：

1. **strict 档提示词改写**（`prompt.go` 的 `todoPromptRule`）。现文案是「动手前先建清单」，
   改写为轮次纪律（保留纯对话豁免，否则打招呼也要建清单）：

   > 每轮开始先审视任务清单：本轮是新任务就用 todo 工具出清单（3~7 条、动词开头、每条
   > 可独立验收）再动手；已有清单先对照现状更新（继续做哪项、完成哪些），不要无视旧清单
   > 另起炉灶。执行中每完成一步立即更新（当前项 done、下一项 active，一次只标一个
   > active），不得攒到轮末一次性补写；纯对话回复（打招呼、答疑、闲聊）可豁免。轮收尾
   > 清单必须与实际进度一致。

   体积影响：strict 档从约 130 字增到约 200 字（+70 字 ≈ 35 token），一次性 system
   成本，可忽略。normal/off 档不动（「每轮必出」是 strict 档的契约强度；off 档用户已
   显式关闭）。

2. **工具结果回显强化**（`formatTodoResult`）。模型每次写清单看到的反馈升级为结构化
   状态 + 下一步指令：

   ```
   清单已更新（5 项：done 2 · 进行 1 · 待办 2）:
   ▶ 写数据模型与状态机
   · 补测试
   ✓ 读现状材料
   ✓ 定稿方案
   · UI 结构
   ```
   全 done 时追加一行：`清单已全部完成。`——给模型一个明确的收敛信号，别在完成后反复改。

3. **不硬门**（不在工具层强制「轮内必须有 todo 调用才许跑其他工具」）：会破坏 off/normal
   档、纯对话轮与续跑场景，且误伤成本（整轮被卡）远大于收益。契约强度靠提示词 + 注入 +
   回显，弱模型出错由硬校验（active≤1、content 唯一、status 合法）兜底——校验报错本身
   就是给模型的纠偏反馈。

### 2.2 派发清单的传递（A2）——推荐「主拆初稿 + 子可修订」

`agent_dispatch` 加**可选**参数 `todos`（`[{content,status}]`，主 Agent 拆好的初始清单，
建议 3~7 条）：

- **传了**：写入子会话 `s.todos` 作为初始快照 + 发一条 `TodoUpdatedEvent`（带 dispatch_id，
  卡上立即出现清单）；任务说明书（`composeTaskMessage`，history[0]）末尾附清单文本，
  子 Agent 的第一眼依据里就有它。
- **没传**：行为与今天完全一致——子 Agent 在 strict 档下自己拆。
- **子会话始终可以修订**：它后续的 todo 调用是全量替换，天然覆盖初稿。

**为什么不写死主拆**：主 Agent 更懂全局优先级（哪个子任务先做、验收标准是什么），但执行
中的自主调整（发现任务比预想简单/复杂、需要拆出新步骤）只有子 Agent 自己知道。写死清单
会逼子 Agent「照着错的清单演」。初始快照 = 给了全局视角又不锁死。
**为什么不纯子拆**：主 Agent 派发时在心里已有拆解，让它显式写出来（a）逼它想清楚验收
边界，（b）用户在派发卡上立刻看到「这次派发要做什么」，不用等子会话第一轮结束。

schema 变更（dispatch.go 的 `DispatchCall` + 参数 schema）：

```json
{ "agent": "...", "task": "...", "session": "...(可选)",
  "todos": [{ "content": "定位泄漏点", "status": "pending" }, ...] }
```

### 2.3 子会话进度同步（A3）

- **内核**：`childEmitter` 把 `TodoUpdatedEvent` 从「拦截」改为「盖 `DispatchID` 上抛」
  （`events.go` 的 `TodoUpdatedEvent` 加 `DispatchID` 字段，与 BusyEvent 2026-10 的
  处理同款）。主时间线随之能归约派发卡徽标；子会话页由既有双投机制吃到（不变）。
  `dispatch.go:173` 的白名单（TapEvent 类型集合）同步放开。
- **wire**：`todo.updated` 载荷加可选键 `dispatch_id`（缺省 = 主会话自己的清单更新，
  前端按 `session_id` 路由的现状不变）。形状向后兼容：老前端多收一个不认识的键，行为不变。
- **主 Agent 上下文感知**：**只在派发结束时**一次性回传——`DispatchResult.Output`（即
  调度结果消息）末尾追加：

  ```
  子会话清单最终状态：3/4 完成，未完成：补集成测试（子会话执行中自行缩减了范围）
  ```
  全部完成则是 `子会话清单最终状态：4/4 完成。`。**轮中不塞**——派发跑在主会话一轮的
  工具循环里，中途注入会打断主 Agent 正在进行的其他并行调用判断；卡上徽标给用户实时看，
  文本给主 Agent 验收时看，两种受众两种通道。续跑场景（`session` 参数）同理：任务消息
  末尾带上一轮定格清单的残留状态，子 Agent 接着跑才知道从哪继续。

### 2.4 防摆设/防残留硬机制（A4，用户最痛的点）

四道闸，覆盖「不更新」「不收敛」「有残留」三种病灶：

1. **轮首快照注入**（摆设的根治）：`runTurn` 开头，若 `s.todos` 非空，把清单现状以
   **通告消息**（复用 `notify.go` 的 noticeMessage 机制、本轮 drain 后注入，不落用户
   时间线）塞进本轮上下文：

   ```
   [当前任务清单] 5 项：done 2 · 进行 1 · 待办 2。进行中：写数据模型与状态机。
   先对照此清单行动：完成即更新、状态如实，不要无视它另起炉灶。
   ```

   「不更新」从「模型不知道自己没更新」变成「每轮都被当面提醒」——这是模型侧唯一可
   感知的闭环，也是比提示词说教强得多的约束（提示词是期望，注入是事实）。

2. **轮收尾校验**（残留的显性化）：`runTurn` 正常收尾（TurnDone）时检查清单——仍有
   active/pending 项 → 给**下一轮**队列塞一条被动通告（`QueueNoticePassive`）：

   ```
   [清单收尾提示] 上轮结束时清单仍有 2 项未完成：补测试（进行中）、写文档（待办）。
   若任务实际已完成请更新清单；若未完成，本轮继续。
   ```
   **不硬阻塞**：多轮长任务轮轮收尾都欠着清单是常态（跨轮任务本来就没做完），硬阻塞
   会把正常节奏卡死。通告入队 = 下一轮模型必然看到，用户在通告条上也看得到。
   busy/错误收尾不校验（那轮本来就没走完，校验只会产生噪声）。

3. **全 done 收敛提示**（残留的反向——假完成）：轮首注入时若清单全 done，通告改为
   「上轮清单已全部完成。若本轮是新任务请重建清单；纯对话可直接回复」——防止上一单的
   旧清单挂着误导本轮。

4. **子会话定格归档**（派发粒度的残留终结）：派发结束时清单定格（见 1.2），未完成项
   在卡上如实显示 + 主 Agent 结果文本点名（见 2.3）。子会话不再有「清单漂在内存里谁也
   不管」的状态——它的终点永远是一个定格的卡。

### 2.5 content 唯一性（A5）

`todo.go` Exec 里加：trim 后 content 重复 → 报错（`第 N 项与第 M 项内容重复，清单项
必须唯一`）。DSH 同款约束；对全量替换语义来说重复项没有任何合法用途，纯噪声。

## 3. UI（DSH 风格，C 组）

### 3.1 计划条升级为 TodoDock 形态（C7）

`TodoList.tsx` 现有骨架（三态图形/折叠/滚动数字）保留，升级三处：

- **头部计数标签**：`✓ 3 · ▶ 1 · ○ 2`（done/active/pending 三段计数，active 段带
  渐变强调色），替代现在的单一 `done/N`；全 done 时整头变绿勾 + `完成 N 项`。
- **进行中进度环**：头部图标在有 active 项时显示**渐变弧**（`stroke-dasharray` 按
  done 占比，conic-gradient 或 SVG 弧），转动动画仅在 `motionAllowed` 时启用（现有
  `.todoHeadPie` 骨架在，补渐变与门控）。
- **折叠交互**保留；默认态 = 折叠（头部一行），`todo.updated` 到达时若有 active 项
  自动展开一次（用户在看进度的场景里，展开的收益大于打扰；全 done 自动收起）。
- 全部走 `agent-console-v3` token（颜色用 `--acc-*`/`--ok-*` 现有变量，不发明新色）；
  挂载位置不动（Composer 计划条是主会话唯一常驻呈现面）。

### 3.2 时间线 TodoRow 摘要行（C8）

`Block` 渲染 `kind:"tool"` 且 `name === "todo"` 时，不再渲染 args JSON 工具行，改为
一行摘要条：

```
☰ 任务清单  ✓ 3 · ▶ 1 · ○ 2  → 写数据模型与状态机
```

（N done · M 进行 · K 待办 + 当前进行项 content；结果里的错误态红字显示校验报错）。
历史回放与实时同构（都是 tool 块，天然一致）。这是「清单出来之后有痕迹」的最小成本
做法——todo 的每次调用在时间线上都留下一次状态跳变。

### 3.3 子会话呈现（C9）

- **子会话页头部**（`ChildSessionPage` 的 `.child-session-head` 下）挂子会话自己的
  TodoDock：数据 = 该子会话 state 的 `todos`（双投已把带 dispatch_id 的 todo.updated
  归约进子会话 state，**前端零新机制**，只加渲染）；定格后显示定格值。
- **主时间线派发卡进度徽标**：dispatch 块加 `todos?: TodoItem[]` 字段。running 时随
  带 dispatch_id 的 todo.updated 实时更新（卡头右侧 `✓ 2/5 · ▶ 定位泄漏点` 一行，
  点击跳子会话）；done 时定格为 finalTodos。**不展开卡内子时间线**（2026-09-30 拍板
  的「卡 = 一行摘要」契约不破——徽标是计数不是内容）。
- 子会话标签页标题旁可加同款计数（低成本，顺手）。

### 3.4 纪律（C10）

全部组件走 `motionAllowed` 门控（进度环转动、计数滚动、展开收起动画）；样式 token 只
用现有 v3 变量；新增测试：`tests/todo-dock.test.mjs`（计数标签/三态渲染/折叠）、
`tests/todo-row.test.mjs`（摘要行渲染与错误态）、`tests/dispatch-todo.test.mjs`
（徽标实时更新与定格）。

## 5. 实施分期（建议三批，每批可独立验收）

**第一批（内核契约，~2 个文件 + store）**：
`todos` 落库/恢复（store + turn.go sink + Latest 读回）→ content 唯一校验 → 回显强化 →
strict 提示词改写 → 轮首快照注入 → 轮收尾校验通告 → 全 done 收敛提示。
验收：重启恢复清单、写重复 content 报错、模拟弱模型不更新时下一轮通告可见。单测钉：
落库往返、唯一性、注入条件（todos 空/全 done/未完成三分支）。

**第二批（进度同步 + UI）**：
TodoUpdatedEvent 带 DispatchID 上抛（childEmitter + events.go）→ wire 三个可选键 →
TodoDock 视觉升级（头部计数/进度环/motionAllowed）→ TodoRow 摘要行 → 派发卡徽标 →
子会话页头部计划条。验收：子会话跑任务时主时间线卡上计数实时跳动、子会话页有计划条、
时间线上 todo 调用有摘要痕迹。前端测试三件套。

**第三批（派发清单 + 定格 + Demo）**：
`agent_dispatch.todos` 参数 → 初始快照 + 任务说明书附清单 → 派发收尾定格归档 +
`finalTodos` + 结果文本追加清单状态 → DemoAgent 同步。验收：主 Agent 拆清单派发、
卡上从第一秒就有清单、结束后定格、主 Agent 下一轮上下文里能看到 N/M。

依赖关系：第二批依赖第一批的落库（徽标定格要读 finalTodos）；第三批依赖第二批的
dispatch 块 todos 字段。批内无相互阻塞，三批可连续做。

## 6. 需要用户拍板的清单

1. **派发清单谁拆**：推荐「主拆初稿（可选参数）+ 子可修订」混合制。备选：纯子拆
   （主不传 todos，简单但用户在派发当下看不到计划）或主拆写死（全局感最强但锁死
   子 Agent 自主调整）。
2. **轮收尾校验严格度**：推荐「被动通告入队，下一轮可见」（不阻塞）。备选：hard 档
   ——收尾未收敛时在 TurnDone 结果上带警告标记（UI 显示黄色点）；更强的「阻塞 + 重试」
   不推荐（会卡死跨轮长任务的正常节奏）。
3. **主会话全 done 清单是否自动清空**：推荐**不清空**（保留成就态与上下文），靠轮首
   收敛提示引导模型在新任务时重建；用户可 `/todo clear`（斜杠命令，第二批或第三批顺手加）
   或等模型下轮全量替换。若用户偏好 DSH 的「用完即清」，改为全 done 后轮首自动清 +
   通告说明，实现成本相同。
4. **「每轮必出」的档位绑定**：推荐只绑 strict 档（normal 档维持按复杂度，off 档
   完全关闭）。若用户要「所有档位都必出」，normal 档文案同步改写即可（一行改动）。
5. **子会话标签页标题计数**：推荐加（`✓ 2/5`，一行文本）；不加也不影响主链路。
6. **TodoRow 是否完全替代工具行**：推荐 todo 调用只渲染摘要行（args 不再展示——
   全量清单 args 对用户是噪声）；若想保留「看模型写了什么全文」的能力，摘要行可点击
   展开 args（多一个交互面，建议先不做）。
